# Source execution evidence

`memcordon-ci source plan --suite SUITE --output PLAN.json` resolves the checked-in structured coverage declarations for a suite. `source attest --plan PLAN.json --journal JOURNAL.json --output ATTESTATION.json` validates a hosted execution journal. `source merge --plan PLAN.json --attestation ATTESTATION.json --output MERGED.json` accepts repeated plan and attestation arguments and requires every declared runner and route on the current commit.

During ordinary suite execution, typed Cargo test commands receive a generated TOML runner configuration containing a native argument array. Cargo still selects packages, features, targets, arguments, working directories and environments. The adapter inherits the outer command's process containment and deadline; it does not create another process group or increase the deadline. It lists all tests, ignored tests and selected tests before running the original binary arguments. Successful libtest counts must agree with those exact inventories. The adapter records binary and output hashes; the parent binds each record to Cargo's compiler artifact, package, target and features, remeasures the binary and rejects missing artifact execution records.

Per-suite/process journals live under `target/ci/source-observations`. They retain actual materialized native arguments, command/output digests, typed toolchains, hosted workflow/run/job/runner identity and final suite status after build-context auditing. A dirty or changed checkout cannot produce authoritative source attestation. Source declarations, command digests, commit, suite and native runner must agree; absent selected tests cannot be inferred from successful compilation or a successful command alone. Original process diagnostics remain visible if evidence processing also fails.

The initial declarations cover seven Windows module-local test files through the native binary target and the package-policy rollback file through the existing protected `windows-package-channel` integration target `sealed_agent`. That transaction already invokes its three exact ignored tests. Its integration target supplies the Cargo binary environment needed by those tests. No additional destructive package transaction is introduced by evidence collection.

`source collect --workflow WORKFLOW --output OUTPUT` collects the current hosted run's initial declared native lanes. `ci/source-execution.toml` maps every currently declared suite/architecture to the checked-in workflow matrix. The collector obtains complete run/job/artifact inventories from GitHub, verifies the downloaded ZIP against the API's SHA-256 digest, binds the run attempt and exact successful emitting job/runner label, and feeds the actual native journal into strict plan attestation and merge. Missing architectures, incomplete inventories, duplicate journals, wrong artifact origins and missing execution fail closed. CI and Backend Certification run this collection after their required native and package-channel jobs; observations are excluded from compiled-output caches.

Deep CI additionally collects its five stress lanes. All five must execute the four runtime-evidence vector tests. Both macOS and both Windows lanes must also execute the exact ignored `deep_short_children_are_bounded_reaped_and_observed` test. Linux's existing backend-availability branch does not establish execution of that lifecycle test, so its declaration covers the unconditional vector tests only. Collection does not change the stress workload, iteration count, deadline or failure behavior.

The three records under `ci/source-evidence-bootstrap` preserve the design baseline's actual successful workflow histories, including its conditional skipped loader-lab job. They are explicitly historical examples with `execution_attested = false`, not hard-coded acceptance policy or evidence for a changed commit.

This remains partial GOV-02. Release preflight enforcement, complete per-source declarations, release workflow integration, Deep fuzz and certification-scenario evidence, and delegated-process evidence propagation remain required. Doctests, custom harnesses and benchmarks are not attested as native libtest behavior by this framework. The source inventory report and raw command journal continue to set `execution_attested` to false; only strict plan validation produces an attestation. A pull-request's synthetic merge checkout is accepted only within its own trusted collecting run; future release admission must require a completed successful run for the exact candidate commit.
