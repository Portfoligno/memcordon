# Windows sealed provider protocol v1

The public and private Windows provider protocols use bounded, length-prefixed JSON frames over fixed local named pipes. Frame length is a little-endian `u32`, payloads are limited to 16 MiB, unknown fields or versions are rejected, and no field is interpreted by a shell.

The public protocol on `\\.\pipe\memcordon-sealed-agent-v1` supports `Probe`, `RecoveryStatus`, elevated `PackageCleanup`, `Launch`, `RelaysReady`, `Cancel`, and `RelaysRetired`. Responses are `Probe`, `RecoveryStatus`, `PackageCleanupReady`, `StreamsPrepared`, `TargetAuthorized`, `TargetRetired`, `Terminal`, or typed `Reject`. The launch request contains a nonce, native UTF-16 program and argument arrays, environment entries, current directory, and typed policy. It never contains an authoritative caller identity, token, provider path, pipe, Job, or guardian handle.

The control service derives private `Membership` and `Launch` requests for `\\.\pipe\memcordon-sealed-launcher-v1`. The broker request binds an attempt id and request digest to kernel-authenticated process identity, a canonical caller-token envelope, and non-inheritable handles duplicated directly into the launcher. Handle values are never accepted from the public caller.

The stream response returns exactly three frontend-side pipe handles. The frontend validates that each is a pipe, starts all relays, and acknowledges `RelaysReady` before target creation. Membership and every subsequent attempt frame bind the protocol version, attempt id, launch nonce, and canonical request digest. After the launcher reports `TargetRetired`, the frontend joins all relays and acknowledges `RelaysRetired`; only then may the launcher issue the terminal receipt. Probe, recovery, package mutation, and rejection before durable launch admission are explicitly non-attempt operations.

Every rejection records whether a target was created and released. A terminal receipt is acceptable only when its attempt id matches, the Job v2 evidence is internally consistent, and restart-safety proof establishes direct-child reap, workload emptiness, helper reap, boundary retirement, and inability to contain a live process.

An ephemeral-CI installation additionally admits the typed `CertificationMutant` request and bound `CertificationMutantHookObserved` or `CertificationMutantObserved` responses. These messages are unavailable to ordinary installations and public launches. A hook receipt identifies the exact changed native operation; when an external readback is required, it transfers one non-inheritable query-only target-process handle that the authenticated certification frontend adopts before validation. Retirement-mutant receipts contain the forbidden terminal candidate. Promotion accepts a mutant only when the independent checker rejects the retained native facts; generic process-creation errors, selector names, and self-reported booleans are not evidence.
