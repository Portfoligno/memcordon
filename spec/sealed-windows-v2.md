# Windows sealed mechanism v2

`windows-job-object-v2` is available only through the installed, qualified MemCordon Windows provider. The public request remains `memcordon --sealed -- COMMAND ARGUMENT...`; callers cannot select service identities, pipes, tokens, Jobs, handles, guardians, or cleanup operations.

The public `MemCordonSealedControl` service runs as restricted-service-SID LocalService. It owns `\\.\pipe\memcordon-sealed-agent-v1`, authenticates its peer with named-pipe process identity plus impersonation, captures a primary token and canonical caller-token envelope, rejects callers already in an active sealed Job, and never executes caller code. The private `MemCordonSealedLauncher` service runs as restricted-service-SID LocalSystem, owns `\\.\pipe\memcordon-sealed-launcher-v1`, accepts only the installed control service, and alone creates Jobs and processes.

Each attempt creates a fresh unnamed Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, no breakaway flags, an I/O completion port, and read-back-verified memory limits. Before target creation, the launcher starts an independent guardian holding the Job, frontend, per-attempt launcher-worker, disarm, and readiness handles, plus the attempt id and bounded cleanup deadline. The guardian acknowledges readiness before any target exists and calls `TerminateJobObject` if the frontend or launcher worker disappears. It waits for native Job accounting to reach zero and atomically writes a separate authenticated guardian terminal receipt. Startup recovery is the sole owner that merges that receipt with the authenticated attempt record, so guardian and launcher never concurrently replace the same record and recovery never infers descendant cleanup from direct PIDs.

The guardian command also receives a native readiness-delay value. It is fixed to zero for ordinary launches; only the ephemeral executable-mutant gate supplies a bounded nonzero value so an external marker can prove that an early-resume mutant actually executes before readiness.

The target is created with the authenticated caller's primary token and native UTF-16 program, argument vector, environment, and working directory. `STARTUPINFOEXW` contains `PROC_THREAD_ATTRIBUTE_JOB_LIST` for creation-time assignment and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` for exactly stdin, stdout, and stderr. The target remains suspended until token-envelope equality, Job membership, limits, and inherited-handle policy are read back. Authorization is exactly one `ResumeThread` transition from suspend count one.

Containment is credential-neutral: later token changes, alternate-token descendants, elevation, daemonization, and nested child Jobs do not remove membership in the outer non-breakaway Job. AppContainer callers are rejected in v1 because their complete launch envelope is not yet supported.

Terminal cleanup calls `TerminateJobObject`, waits for `ActiveProcesses == 0`, reaps the direct process and guardian, retires stream relays, retires the authenticated durable attempt record, removes the Job from the recursive-request registry, and closes the final Job handles. Any missing predicate is a sealed failure, never standard fallback or ordinary child success.

The provider persists only recovery metadata under `%ProgramData%\MemCordon\sealed`; it never persists command arguments, environment values, or stream data. Startup reconciles authenticated non-retired records with guardian and process identity. Ambiguous state quarantines the record and keeps qualification unavailable.

Execution evidence is `WindowsSealedEvidenceV2` under execution report schema 8. It binds caller authentication, token reproduction, creation-time Job and handle lists, suspended verification, guardian readiness, termination, Job emptiness, relay retirement, guardian reap, and final Job-handle closure. Qualification receipt schema 1 must prove every native predicate before the client advertises sealed capability.
